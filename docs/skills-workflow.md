# Регламент: добавление и обновление навыков

Что происходит само, а что надо сделать руками, когда вы правите или добавляете навык
в `skills/`.

## Коротко

| Что | Как обновляется |
|---|---|
| Проверка навыков | **Автоматически** при пуше в `skills/` и в pull request |
| ZIP-архивы навыков | **Автоматически**, если проверка прошла |
| Релиз `skills-latest` | **Автоматически**, той же сборкой |
| Ссылки для скачивания | Не меняются никогда — постоянные |
| `README.md`, `skills/README.md` | Руками |
| `CHANGELOG.md` | Руками |
| Описание репозитория (About) | Руками |
| Страница MCP на сайте | Руками |
| Карточка в Cursor Directory | Руками, через Re-scan |
| Реестр MCP | **Автоматически** при изменении `server.json`, с проверкой версии |
| Реестр MCP при правке навыков | Не затрагивается — навыки в `server.json` не описаны |

Ссылка на архив собирается по имени папки:

```
https://github.com/Rusender/rusender-mcp/releases/download/skills-latest/<имя-папки>.zip
```

Поэтому **переименование папки ломает ссылку на сайте**. Если переименовываете —
обязательно правьте и сайт.

---

## Что делают workflow

В репозитории два workflow. Они решают разные задачи и запускаются по-разному.

### `build-skills.yml` — сборка архивов навыков

**Когда:** автоматически при пуше в `master`, если изменения затронули `skills/`.
Плюс при любом pull request с изменениями в `skills/`. Плюс вручную через
Actions → Build skill archives → Run workflow.

**Что делает:**

1. Джоба **check** — ставит PyYAML и запускает `scripts/check-skills.sh`.
   Проверяет фронтматтер каждого навыка, ищет посторонние почтовые адреса,
   внутренние адреса и туннели, похожее на секреты, сверяет число папок
   с таблицами в обоих README.
2. Джоба **build** — запускается только после успешной проверки (`needs: check`)
   и только вне pull request. Собирает ZIP из каждой папки навыка и публикует
   их в релиз с тегом `skills-latest`, перезаписывая предыдущие файлы.

**Что на выходе:** постоянные ссылки вида
`https://github.com/Rusender/rusender-mcp/releases/download/skills-latest/<имя>.zip`.
Они не меняются между сборками, поэтому их можно смело ставить на сайт.

**Когда упадёт:** нет `SKILL.md`, `name` не совпадает с папкой, нет `metadata.version`,
`description` или `license`, найдено похожее на секрет. Предупреждения
(`description` через `>-`, моковые ngrok-адреса, расхождение README) сборку не ломают.

**Трогать его нужно**, только если меняется сам порядок сборки: например, вы решите
исключить какой-то навык из публикации или добавить ещё одну проверку.

### `publish-mcp.yml` — публикация сервера в реестре MCP

**Когда:** автоматически при пуше в `master`, если изменился `server.json`.
Плюс вручную через Actions → Publish to MCP Registry → Run workflow.
На остальные коммиты не реагирует — навыки, README и документация реестра не касаются.

**Что делает:**

1. Запускает `scripts/check-registry-version.py` — сверяет `version` из `server.json`
   с тем, что уже опубликовано в реестре. Если версия совпадает, останавливается
   и пишет в лог, какой номер поставить.
2. Скачивает утилиту `mcp-publisher`.
3. Авторизуется через GitHub OIDC. Права на namespace `io.github.Rusender` выдаются
   по владельцу репозитория — токенов и членства в организации не требуется.
4. Публикует `server.json` в `registry.modelcontextprotocol.io`.

**Что на выходе:** запись сервера в официальном реестре MCP. Оттуда её подтягивают
агрегаторы: Metatext, PulseMCP, MCP Central и другие.

**Когда упадёт:** версия в `server.json` совпадает с опубликованной. В логе будет
подсказка по нумерации. Если реестр недоступен, проверка пропускает вперёд и
публикация всё равно пробуется.

**Порядок работы:** меняете `server.json`, поднимаете в нём `version`, пушите.
Публикация уйдёт сама. Забыли поднять версию — увидите красный крестик с объяснением,
поправите и запушите снова.

**Как нумеровать:**

- патч `1.0.1` — правка описания, ссылок, названия
- минор `1.1.0` — новые возможности сервера
- мажор `2.0.0` — смена URL или способа подключения

**Менять `server.json` нужно**, только когда меняется сам MCP-сервер: другой адрес,
другая авторизация, переписанное описание, переехавший репозиторий. Новые инструменты
в сервере повода не дают — реестр их список не хранит. Навыки на реестр не влияют вовсе.

Проверить, что опубликовалось:
`https://registry.modelcontextprotocol.io/v0/servers?search=rusender`

## Проверка перед коммитом

Локально, из корня репозитория:

```bash
bash scripts/check-skills.sh
```

Занимает пару секунд, ничего не меняет и никуда не отправляет. Смысл — увидеть ошибку
до пуша, а не через минуту после.

Можно повесить на git-хук, чтобы запускался сам:

```bash
cat > .git/hooks/pre-commit << 'EOF'
#!/bin/bash
if git diff --cached --name-only | grep -q "^skills/"; then
  bash scripts/check-skills.sh || exit 1
fi
EOF
chmod +x .git/hooks/pre-commit
```

Хук живёт в `.git/` и не коммитится: на новой машине и у коллег его придётся ставить
заново. На это можно не полагаться — проверка в CI всё равно сработает.

## Чек-лист: новый навык

### 1. Файлы навыка

- [ ] Папка `skills/<имя-навыка>/`, имя в нижнем регистре через дефис
- [ ] Внутри `SKILL.md`, при необходимости `assets/` и `references/`
- [ ] Поле `name` во фронтматтере **точно совпадает** с именем папки
- [ ] `description` записан **одной строкой в кавычках**, не через `>-`
- [ ] Есть `license: MIT`
- [ ] Есть `metadata.version`, начинаем с `1.0.0`

### 2. Проверка на лишнее

- [ ] Нет боевых email подписчиков и сотрудников
- [ ] Нет реальных id кампаний, только вымышленные
- [ ] Нет внутренних адресов, туннелей, тестовых доменов
- [ ] Нет ключей, токенов, паролей

```bash
bash scripts/check-skills.sh
```

### 3. Коммит

- [ ] `git add` и пуш в `master`
- [ ] Actions: джоба **check** зелёная, **build** отработала
- [ ] Releases: архив появился

### 4. Обновить вручную

- [ ] Таблица в `README.md` — строка с названием, описанием и ссылкой на ZIP
- [ ] Таблица в `skills/README.md` — то же плюс версия и ссылка на инструкцию
- [ ] `CHANGELOG.md` — запись в новый блок с датой
- [ ] Описание репозитория в блоке About, если поменялось число навыков

### 5. Сайт

- [ ] Карточка на `rusender.ru/features/email/mcp/`
- [ ] Кнопка «Скачать скилл» ведёт на ссылку релиза
- [ ] Страница инструкции `rusender.ru/features/email/mcp/skill-<...>/`

### 6. Каталоги

- [ ] Cursor Directory: на странице плагина нажать Re-scan, проверить, что навык подхватился
- [ ] Если меняли `plugin.json` — поднять в нём `version`

## Чек-лист: правка существующего навыка

### Обязательно

- [ ] Поднять `metadata.version` в `SKILL.md`
      (правка текста → патч 1.0.1, новая возможность → минор 1.1.0,
      сломана обратная совместимость → мажор 2.0.0)
- [ ] Прогнать `bash scripts/check-skills.sh`
- [ ] Запушить, убедиться что проверка прошла и релиз пересобрался

### Если менялось описание или состав

- [ ] Обновить строку в `README.md`
- [ ] Обновить строку и версию в `skills/README.md`
- [ ] Запись в `CHANGELOG.md`
- [ ] Поправить инструкцию на сайте, если поведение изменилось

### Если переименовали папку

- [ ] Поменять `name` во фронтматтере на новое имя папки
- [ ] Поправить ссылки в обоих README
- [ ] **Поменять ссылку на кнопке на сайте** — старая перестанет работать
- [ ] Re-scan в Cursor Directory

## Чего делать не нужно

**Запускать «Publish to MCP Registry» после правки навыков.** Он описывает
MCP-сервер, а не навыки, и срабатывает сам при изменении `server.json`. Ручной запуск
без поднятой версии остановится на проверке.

**Перезаливать архивы на сайт.** Ссылки ведут на релиз, файлы обновляются сами.

**Собирать ZIP руками.** Это делает workflow. Архивы в репозитории не хранятся.

## Если что-то пошло не так

**Джоба check упала.** Раскройте шаг «Проверить навыки» — там написано, какой навык и
что именно не так. Почините, запушьте снова.

**Релиз не обновился.** Actions → последний запуск → шаг «Собрать архивы». В логе видно,
какие папки собрались и какие пропущены. Частая причина: в папке нет `SKILL.md`.

**Пуш отбивается с упоминанием `workflow` scope.** Токену не хватает прав на файлы в
`.github/workflows/`. Нужен classic-токен со скоупами `repo` и `workflow`, либо переход
на SSH — тогда токены не нужны вовсе.

**Публикация в реестр остановилась на проверке версии.** В логе шага «Сравнить версию
с реестром» написано, какая версия уже опубликована. Поднимите `version` в `server.json`
и запушьте — публикация уйдёт сама.

**Сборку надо запустить вручную.** Actions → Build skill archives → Run workflow.
